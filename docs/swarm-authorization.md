# 个人 swarm 的创建与授权需求

**状态：需求草案，尚未实现完整流程。**
中心服务（每个 swarm 一个可变 `HEAD` 的签名指针）已有实现：
[packages/pointer-worker](../packages/pointer-worker)。CLI 的设备授权、命名域解析与
跨设备同步仍未实现。
本文细化[项目愿景](../VISION.md)中的个人 swarm 接入场景：
我在电脑上创建 swarm，授权笔记本加入；此后两台设备上的 Agent 都能读取和更新同一份
Artifact 映射，无需共享私钥，也无需我批准每一次发布。

## 授权保护什么

中心服务为每个 `swarmAID` 维护**一个**可变的 `HEAD`，并登记该 swarm 的根公钥。
`swarmAID` 用来选中哪个 swarm，不是密码。`HEAD` 是当前发布记录的 CID；
发布记录引用映射表的 Merkle DAG 根及上一次发布（首次发布没有前序）。
成员读取一次 `HEAD`，即可按需从 IPFS 获取同一快照中的 `AID → CID` 映射。
中心服务不为每个 Artifact 建立变量，不存储或遍历映射表。

所有有效成员都能读 `HEAD`，也都能尝试更新它；非成员两者都不能做。
成员写入权不包括签发成员证书或替换根公钥。服务认证的是证书绑定的设备身份：
同一设备上的多个 Agent 如果共用设备密钥，服务不区分它们。

## 场景一：我创建自己的 swarm

我在本地生成 swarm 根密钥对，自己保管根私钥，只向中心服务提交公钥。
服务通过一次性挑战验证我持有对应私钥，并将
`swarmAID`、根公钥和初始 HEAD 状态绑定。
即使有人知道 `swarmAID`，用另一个密钥对重新注册也不能覆盖已有绑定。
创建完成后，根私钥不上传，也不参与设备日常的 HEAD 读写。

## 场景二：我授权一台新设备加入

笔记本在本地生成**自己的**设备密钥对，只把公钥交给我。我确认待加入设备的公钥，
用 **swarm 根私钥**签发成员证书，将 `swarmAID`、设备公钥和有效期一起签入证书。
笔记本收到证书，保留自己的私钥；它不需要取得根私钥或其他设备的私钥。
创建 swarm 的电脑若也作为成员运行 Agent，同样使用独立的设备身份。

证书证明“这个 swarm 接纳了这个公钥”，并不证明“出示证书的人持有设备私钥”。
因此把笔记本的证书复制到另一台机器，不足以让后者读写 HEAD。

## 场景三：新设备首次读取 HEAD

笔记本通过 HTTPS 取得服务的一次性挑战，用**设备私钥**签发短期请求凭证
（access token），连同成员证书一起提交。凭证绑定目标服务、`swarmAID`、操作、
该操作的参数、挑战及过期时间。不把它当作可重复使用的 bearer token。

服务在返回 HEAD 或执行写入前，必须完成两项独立验证：

1. **验证成员资格。** 按请求的 `swarmAID` 查到已登记的根公钥，验证证书签名、
   所属 swarm 和有效期。不采信请求方自行提供的根公钥。
2. **验证本次请求。** 用证书中的设备公钥验证凭证签名，核对签名覆盖的内容与
   实际请求一致；验证时效并一次性消费挑战，不能让同一凭证被再次接受。

通过验证后，读操作返回当前 HEAD。验证失败时拒绝请求，不返回 HEAD，也不修改状态。
读凭证不能改作写凭证，另一 swarm 的合法成员也不能借此访问本 swarm。

## 场景四：两台已授权设备同时发布

电脑和笔记本均读到发布根 `R0`，分别构造新根 `R1`、`R2`。两者都有权发布，
但写请求必须签入**预期旧根和候选新根**。服务验证身份后，以持久、原子的
比较并交换（CAS）更新整个 swarm 的 HEAD：

- 电脑请求 `R0 → R1`。若当前仍为 `R0`，服务将 `R1` 持久化后确认成功。
- 笔记本随后请求 `R0 → R2`。此时基线不匹配，服务向该成员返回冲突和当前根 `R1`，
  保持 HEAD 不变。笔记本的成果仍可保留，但尚未发布。

笔记本应基于 `R1` 重新检查、整合修改后再发布，不能仅替换预期根并重发旧候选根。
即使映射表后来恢复到原来的内容，恢复操作也是一次新的发布，旧请求不能因此重新生效。

## 验收边界

- 无需为每个 AID 登记权限。两台设备凭各自的证书和私钥，都能读取同一个 HEAD，
  也能在基线匹配时发布。
- 仅知道 `swarmAID`、仅持有证书、使用错误私钥、使用过期证书或凭证，都不能读写。
  重放请求、跨服务或跨 swarm 复用凭证、替换已签名的新根，同样不能成功。
- 两个基于同一旧根的竞争更新最多一个成功；服务重启后，已确认的 HEAD 不回退。
  中心服务离线时仍可处理手头的内容，但不能宣称已确认新发布。
- 保护 HEAD
  **不等于加密 IPFS 内容**。知道某个 CID 且可取得其块的参与者仍能读取那个快照；
  HEAD 更新成功也不证明其他设备已经取得新块。内容保密和跨设备可获取性是独立需求。

证书与凭证的编码、签名算法、`swarmAID`
的生成方式、首个 HEAD 的表示、设备撤销与续期、
根密钥轮换与遗失恢复均待后续设计。本文不规定 CLI 或网络接口格式。
